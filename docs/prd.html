SpecGate —— 動工前的規格閘門

一張 Jira 卡 = 一頁規格閘門。動工前先過閘，決策留痕，答案可被程式讀取。

2026-08-18 · Sam · 待驗證（配合 prototype/KAN-15.html 一起看）

1要解決什麼問題

現在的開發流程是：Claude 在聊天視窗給一份實作報告 → Sam 讀 → 口頭回「approve」或「改這個」→ 開始寫。 這個流程有三個洞：

洞具體長怎樣
決策會被沖走 「為什麼第一個來源不是 104」這種判斷只存在於聊天記錄裡。三週後回頭看程式碼，只看得到結果，看不到當時排除了什麼、為什麼排除。面試被問「你怎麼做技術選型」時，答案得靠回憶。
回答是自然語言，程式讀不到 「用 A3 但門檻降到 50 筆」這句話沒有結構。無法統計「這個專案做過幾次選型決策」，也沒辦法在卡關閉時自動比對「當初的驗收條件真的都滿足了嗎」。
單人流程無法擴到團隊 團隊裡「動工前先對規格」這件事通常靠開會或 RFC 文件，成本高到大家會跳過。跳過的結果是 code review 才發現方向錯，重寫成本最高。
核心洞察：code review 是在「已經寫完」之後才發生的。真正該被 review 的是動工前的那個決定 —— 但業界沒有輕量的工具做這件事，所以大家用開會代替。SpecGate 把這一層變成一個頁面、五分鐘、留下結構化紀錄。

2使用者與情境

角色現在（Phase 1）未來（Phase 3 團隊版）
提案者 Claude —— 產出實作報告頁 任何工程師，或 AI agent
審核者 Sam —— 讀、答題、按閘門 Tech lead / 同儕 / PM（依決策類型分流）
執行者 Claude —— 讀答案後動工 工程師或 agent，拿著已批准的規格開工

關鍵情境：Sam 在通勤或睡前用手機讀報告、點選項、按儲存。隔天坐到電腦前跟 Claude 說一句「答完了」， Claude 讀檔就直接開工。審核跟執行在時間上解耦。

3核心概念

一張 Jira 卡對應一頁。頁面同時是三個東西。

① 提案文件

動工前

八節結構的實作報告：目標、現況、關鍵決策點、檔案清單、介面草稿、測試策略、驗收對照、風險與債。

② 決策表單

審核時

報告內文中穿插題目（單選 / 是非 / 問答），問題緊貼在相關段落旁邊 —— 不是集中在最後的問卷。

③ 決策紀錄

動工後永久

答完存成結構化 JSON，跟卡號綁定。這份紀錄之後可以匯總成 ADR、面試素材、團隊決策資料庫。

刻意的限制：一張卡一頁，不做多卡合併頁。閘門的價值來自「單一決定、單次審核、明確結果」—— 一旦一頁塞多張卡，審核就會退化成瀏覽，跟現在讀聊天記錄沒兩樣。

4流程

③④ 是 Sam 的部分，設計目標是 五分鐘內完成。超過五分鐘代表報告寫太長，是 Claude 的問題不是流程的問題。

5功能需求

優先功能說明與驗收
P0 八節報告結構 固定順序、固定標題。第 3 節「關鍵決策點」永遠在最上方顯眼處 —— 那是唯一需要 Sam 動腦的部分。
P0 三種題型 單選（選項含代價/風險，建議項標星）、是非、問答（多行文字）。每題可附備註。
P0 題目穿插在內文 問題出現在相關段落正下方，不是集中在頁尾。讀到哪答到哪。
P0 閘門判定 底部兩顆按鈕：approve 動工 / 要求修改。後者必須填理由才能存。
P0 儲存 → 結構化 JSON 下載到 ~/Downloads/{CARD}-review.json，Claude 直接讀。檔名帶卡號，不會混。
P0 草稿自動保存 每次改動寫進 localStorage。中途關頁面、換裝置以外的情況都不會掉答案。
P1 進度指示 「已答 3 / 5」。未答完時 approve 按鈕停用 —— 強迫每個決策點都被正面回答，不能默認。
P1 索引頁 index.html 列出所有卡的閘門狀態：待審 / 已批准 / 要求修改 / 已完工。
P1 Jira 連動 頁面上有卡片連結與即時狀態。approve 時順手把卡移到「進行中」（走 Rovo MCP）。
P2 決策匯總 把所有 JSON 匯成一頁「這個專案做過的技術決策」—— 直接是面試素材與 ADR 來源。
P2 完工回填 動工完成後，頁面顯示「實際做出來的 vs 當初報告的」差異，把偏離記下來。
P2 多人審核 同一頁多個 reviewer、留言串、分流規則（架構決策找 tech lead、範圍決策找 PM）。

6資料模型

一次審核產出一個 JSON。這個形狀是整個系統的合約 —— 頁面怎麼改，這個形狀盡量不動。

{
  "schema_version": 1,
  "card": "KAN-15",
  "title": "[Phase 0 / W1] 104 adapter：SourceAdapter 介面 + fixture 測試 + crawl_runs 落地",
  "report_version": "2026-08-18T16:40:00+08:00",   // 對應哪一版報告
  "reviewed_at": "2026-08-18T22:15:03+08:00",
  "reviewer": "sam",
  "verdict": "approved",                            // approved | changes_requested
  "verdict_note": "",
  "answers": [
    { "id": "A", "type": "single",  "question": "第一個來源接誰",
      "choice": "A3", "choice_label": "先接有正式 API 的來源（Remotive）", "note": "104 之後再說" },
    { "id": "B", "type": "boolean", "question": "加 tenacity？", "value": true,  "note": "" },
    { "id": "C", "type": "single",  "question": "≥200 筆門檻", "choice": "keep", "note": "" },
    { "id": "D", "type": "text",    "question": "其他條件或反對理由",
      "text": "adapter 介面要能同時容納中英文 JD" }
  ]
}
為什麼要 report_version：報告會改版（要求修改後重發）。答案必須綁定「回答的是哪一版」， 否則之後對照時會出現「他批准的東西跟最後做的不一樣」卻查不出斷點。

7技術架構 —— 三階段，別一次做到位

Phase 1 · 純靜態檔

現在 · 零基礎建設

做法：Claude 產生獨立 HTML，雙擊用瀏覽器開。儲存＝觸發下載 JSON 到 ~/Downloads，外加 localStorage 草稿。

代價：每次存檔多一次下載動作；索引頁要手動維護；答案檔散在下載資料夾。

為什麼先做這個：驗證「這個流程本身有沒有用」不需要任何伺服器。如果流程沒用，省下所有基礎建設。

Phase 2 · 本機小服務

流程證明有用之後

做法：一支 FastAPI（複用 JobRadar 的 stack），GET /cards 列表、GET /cards/{key} 出頁面、POST /cards/{key}/review 存檔。答案落 SQLite 或直接寫 JSON 檔進專案資料夾。

換來：一鍵儲存、自動索引頁、Jira 狀態即時同步、決策匯總頁。

代價：要記得把服務跑起來（可用 launchd 開機自動啟動）。

Phase 3 · 團隊版

有第二個人用的時候

做法：部署上去、加登入、多 reviewer、留言串、Jira webhook 雙向同步。

前置條件：Phase 1–2 至少累積 20 張卡的實際使用，證明流程在單人狀態下不會被跳過。

風險：團隊版最大的敵人不是技術，是「大家覺得多一道手續」。所以五分鐘完成是硬指標。

技術選型註記：Phase 2 刻意用 FastAPI 而非現成工具（Notion / Confluence / Google Forms）—— 因為答案要被 Claude 直接讀取並轉成行動。現成工具的匯出格式都要多一層轉換，而那層轉換就是流程斷掉的地方。

8非目標

  • 不取代 Jira —— 卡的建立、狀態、排序都留在 Jira。SpecGate 只負責「動工前那一刻」。
  • 不是文件庫 —— 不放架構文件、不放會議紀錄。一頁只服務一張卡的一次決定。
  • 不做即時協作 —— 不是 Google Docs。審核是非同步的、一次性的。
  • 不自動產生報告內容 —— 報告是 Claude 寫的，SpecGate 只提供承載與收集的容器。工具不負責想。
  • 不做通知系統 —— Phase 1–2 靠 Sam 自己開頁面。加通知是團隊版才有意義的功能。

9成功指標

指標目標為什麼是這個
審核耗時≤ 5 分鐘 / 張超過就會開始跳過。這是流程存亡的門檻，不是效率優化。
閘門覆蓋率Phase 0 剩餘卡 100%選擇性使用等於沒有流程。
「要求修改」比例20–40%太低代表 Sam 沒在認真審（橡皮圖章）；太高代表 Claude 的報告品質不穩。這個指標同時在監督兩邊。
動工後方向翻盤次數→ 0閘門的最終價值：寫到一半才發現方向錯的次數應該歸零。

10待確認（prototype 要驗證的）

  1. 題目穿插 vs 集中頁尾 —— 穿插理論上更好，但可能打斷閱讀節奏。prototype 用穿插，實際點過再判斷。
  2. 八節會不會太長 —— 手機上讀八節報告可能太重。要不要預設摺疊只展開「決策點」那節？
  3. 未答完就鎖住 approve，會不會太煩 —— 有些題目 Sam 可能真的沒意見想跳過。要不要允許「交給你決定」這個選項？
  4. 下載到 ~/Downloads 夠不夠用 —— 或是該直接跳 Phase 2 做本機服務。這題答案取決於前三題實際用起來的摩擦。
先別做的事：索引頁、Jira 連動、決策匯總都是 P1/P2。在確認「這個流程 Sam 真的會用」之前做這些， 是把時間投在還沒被驗證的假設上 —— 也正是 JobRadar 雙視角手冊裡那條 PM 自我警告：「加功能逃避核心問題」。
